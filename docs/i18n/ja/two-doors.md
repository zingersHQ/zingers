# ZINGERS: 一つの魂、二つの扉（製品フレーム決定）

> **要約:** 本ドキュメントは「この製品は何になるのか？」に答える。製品全体のアイデンティティ決定である。**フライトがゲーム**だ。脊椎であり、顔であり、ブランドであり、誰でも最初に触れるもの。**戦いは登り道で出会うもの**だ。登頂が明かす深みであり、さらに高く登るためのもの。**モバイルが顔**（誰でもゼロ秒で始められるバス待ちフライト）。**デスクトップが完全な世界**（同じフライトの魂に加え、その上を昇る生きた地図）。AIエージェント層は見えないエンジンであり、ファンタジーとして売られ、技術として売られることはない。暗号資産は燃料として横に置かれる。

Version 2.1 · 2026年7月（**Flight-First**、`design-vision.md` v3.1と整合）。決定記録＋実装計画。  
関連文書: [`design-vision.md`](./design-vision.md), [`essence.md`](./essence.md), [`long-game.md`](./long-game.md), [`mobile.md`](./mobile.md)（§3のデフォルト扉は本書で置き換え）、[`vocabulary.md`](./vocabulary.md)。表記はvocabulary.mdに従う。識別子／アナリティクスキーは表記理由で変更しない。

## 0. 五行でまとめた決定

1. **フライトがゲーム。** スマホとデスクトップで一つの魂。戦いは削除・縮小ではなく、*製品そのもの*から*登り道で出会うもの*へ**再配置**される（[`flyover.md`](./flyover.md), `design-vision.md` v3.1参照）。
2. **一つのフライトに二つの扉。** *モバイルが顔*：片手で完結するバス待ちフライト。チャンピオン／観戦／順位が、フライトが飛ぶ世界として徐々に明かされる。*デスクトップが完全な世界*：同じフライトの魂を六自由度で体験し、ハブや地域で深い育成が行われる。どちらも他方の残り物ではない。
3. **エージェントはエンジンであり、売り文句ではない。** プレイヤー向け画面はファンタジーを売る（「生き物は本当に考えている」）。「エージェント」という言葉は開発者向け画面（`/agents`、ドキュメント、プロトコル）のみに残す。
4. **暗号資産は燃料のまま。** [`zing-model.md`](./zing-model.md)に基づき、$ZINGは任意のプレミアム層、クラウンはオフチェーンでサーバー権威、プレイヤー向け画面で収益を約束しない。コレクターは後に来歴をミントやトレードできるが、新しいチャンピオンを鍛えることはない。
5. **今はウェブファースト、後でプラットフォーム。** Steam／コンソールはLaunch v0.1のゲートが緑になった後のマーケティング施策であり、今はエンジニアリング案件ではない（§6）。

**一行要約:** *君は飛ぶ。それが戦う。共に高みへ。* スマホで誰でも30秒で始められるフライトが、デスクトップで登り続ける世界へ開く。

## 1. このフレームを選ぶ理由（コミットする根拠）

- ゲームの堀（`AGENCY.md`）は私たちが作るオリジナルIP＋進化する戦いメタ＋伝説をめぐるコレクター文化。いずれも「心が本物である」ことに依存する。だからエージェント層を削って単純なゲームにはしない。ただし、どれも*初見のプレイヤー*に「エージェント」という言葉を必要としない。
- **登り**は見知らぬ人が**ゼロ秒**で理解できる唯一の動詞（`essence.md` §3のFlappy Bird原子）。「今日の戦いを呼ぶ」。`mobile.md` §3が選んだ扉。訪問者がすでにチャンピオンを気にかけている前提だった。冷めた訪問者はそうではない。だから*扉*を変える。*その奥にあるゲームの本体*（タブシェル、観戦レーンの思想）は変えない。
- *一般的な*上昇ゲームはコモディティ（ハイパーカジュアルは競争が激しく、アプリストアなしのWebGLで参入する）。我々の差別化点は魂の糸：*走行がチャンピオンを刻み*、チャンピオンが君の横を飛び、辺境は本物の世界の本物の地域であり、その上を飛ぶ戦いは本当に考えている心だ。**登りはゲームへ導くロビーではない。登り*が*ゲームであり、登るにつれて自分を明かしていく。**
- デスクトップの未解決課題（「人は理解できるか？楽しいか？報酬を感じるか？」）はLaunch v0.1のゲート1–2そのものであり、現在は**未計測**。答えは計装であり、再設計ではない（§5）。

### 本ドキュメントが常に満たすべきテスト

以下の変更はすべて、(a)見知らぬ人の魂への道を短くする、または(b)その道が機能するかを計測する。どちらでもないものは本書の範囲外。

## 2. ナラティブの位置づけ（どこでも言うこと）

**ファンタジーを売り、技術を売らない。** 持っているナラティブ。ハム、ロング・ヴォールト、キーパー、「*心が自分自身に議論して体になる*」。AIが可能にする生き物育成ファンタジー。ポケモンは生き物をステートマシンとして宣伝しなかった。

ルール（すべてのプレイヤー向け画面に適用。ランディング、`/m`、ストアページ、ソーシャルコピー）：

1. **魔法の一文は：** 「生き物は本当に考えている。同じ戦いは二度とない。」「AIエージェント同士が戦う」ではない。
2. **「エージェント」は開発者語彙。** `/agents`、[`agent-protocol.md`](./agent-protocol.md)、`docs/`、MCP画面にのみ置く。ナビゲーションはすでに正しくフレームされている（`lib/play-nav.ts`「Build」グループ）。そのまま維持。タスク：プレイヤー向け文字列の「agent」「AI agent」「LLM」を監査（ランディング `components/home/landing.tsx`、`/m`タブ、`howitworks`、シェアカード）し、ファンタジー表記に置換。**表記のみ変更し、識別子／キーは変更しない**（`vocabulary.md`と`AGENTS.md`に従う）。
3. **暗号資産は本物になるまで不可視。** ローンチ前はゲーム画面に$ZING言及なし。「稼ぐ」約束はどこにもなし。任意のコレクター永続化（トレード、不滅のためのミント）は存在するまでドキュメント内に留める。チャンピオンはスタジオ制作のまま。プレイヤーは集め、作らない。
4. **プレイヤーが得る報酬語彙：** チャンピオンの**体**（キャリアの可視記録）、**順位**（トレーナーランク＋順位表）、**クラウン**、**サガ**、**ライバル**。これらが正直なインセンティブ。「なぜ遊ぶか？」と問われたらこれを前面に。

## 3. モバイル：Flight-firstの扉（`mobile.md` §3「デフォルト扉」を置き換え）

### 3.1 変わらないものと変わるもの

| `mobile.md`から維持 | 本書で変更 |
|---|---|
| 下部タブシェル（`components/mobile/mobile-shell.tsx`）、全5タブ | **デフォルト扉**はTodayタブではなくなる |
| スマホ＝観戦／予測／共有レーンの*奥行き*が扉の奥にある | *扉*は登り（まず行い、後で気にかける） |
| 「一つの魂、ネイティブな体」、すべての動詞の原子 | 登りに**ゲストモード**を追加（3.3参照。原子は維持） |

### 3.2 最初の画面：ポスター

`/m`（またはPlayからルーティングされたスマホ、`lib/play-nav.ts` `MOBILE_PLAY_HREF`）への冷めた訪問者はタブグリッドではなく**フルスクリーンスプラッシュ**を得る：

- **アート：** エピック画像。ジェットパックで飛ぶトレーナーと、その横を飛ぶチャンピオン。（正典準拠：*トレーナーは飛び、チャンピオンは戦う*）
  - アセット：レンダリング済みポスター。優先順位：(a)静止画アセット（最速、最も制御可能。**制作が必要**、本フェーズ唯一の外部依存）；(b)`ChampionPortraitScene`＋ジェットパックリグを再利用したライブR3Fシーン（新規アート不要だが、初回描画時のWebGLコスト大）。(a)から開始。
- **表記：** ブランド＋タグライン＋一行のファンタジー。提案：`ZINGERS` / *"心を育てる。伝説にせよ。"* / 主要CTA **"FLY"**。
- **CTA：** 主要 **Fly** → 即座にフライトへ（ゲスト／所有、3.3）。副次的（小さめ）：**"君のチャンピオン"**（所有トレーナー）または**"これは何？"**（→ Todayタブ / howitworks）。所有チャンピオンを持つリピーターは初回セッション以降スプラッシュをスキップ可能（3.5フラグ参照）。
- **新コンポーネント：** `components/mobile/mobile-splash.tsx`。`MobileShell`がタブ前状態としてマウント。`lib/brand.ts` `STORAGE`にセッションスコープの却下フラグ（例：`mSplash: "zingers_m_splash_v1"`。sessionStorageのため、新セッションの冷めたオープンでは毎回ポスターを表示するが、セッション内ナビゲーションでは再割り込みしない）。

### 3.3 ゲストフライト（扉を可能にする設計決定）

現在、Flightタブはチャンピオン請求まで**ロック**されている（`mobile-shell.tsx` `climbLocked`、約50行目）。バス待ちの扉はロックで開かない。決定：**ローンアーでアンロック**。

- **ローンアー：** 「野生の心」。現在の週次ローテーションから決定論的に選出（`firstDuelStarterKeys()`、`lib/first-duel.ts`）。ゲストは本物のチャンピオンが横を飛ぶのを見、プレースホルダーではない。デバイス・トークンからシードを選ぶことで、同じ訪問者が「自分の」野生の心に繰り返し出会う（養子縁組前の愛着）。
- **原子の維持**（`essence.md` §2：走行が*チャンピオンを刻む*）：ゲスト走行は**何も刻まない**。それがフックであり、違反ではない。ゲスト走行中／後にバナー：「野生の心が君と飛んでいる。**請求して**登りを残せ。」請求時、現在の走行の最高到達深度が最初のキャリアマークに変換される（一回限り、養子縁組までクライアント保持、その後通常の登り報酬経路で書き込み）。
- **順位表：** ゲスト走行はリーダーボードに書き込まない（所有チャンピオンなしでは`/api/circuit` POSTが単に呼ばれない。`circuit-lite.tsx` `recordRun`の既存ゲーティングを反映）。ゲスト用に新規サーバー画面不要。
- **請求の瞬間：** 落下後（自然な間）にリトライカードに二番目のボタン追加：**"この心を請求"** → 既存の選択画面（Championタブ経由の`components/mobile/mobile-adopt.tsx`）。ライブ走行を獲得UXで中断しない。
- **コード接点：** `mobile-shell.tsx`（ロック解除→`loaner`プロパティでゲストを登りにルーティング；ロック*ロジック*は「ゲストである」シグナルとして維持）、`circuit-lite.tsx`（`guestChampion?: string`プロパティを受け入れ、ゲスト中は順位表／報酬書き込みを抑制、請求バナーを表示）、`mobile-adopt.tsx`（事前選択キーを受け入れ、「この心を請求」が野生の心に着地するように）。

### 3.4 扉の奥のシェル

構造は変更なし（Today · Watch · Champion · Flight · Rank）、二つの調整：

- **ゲストとして登りを退出**すると**Champion**（請求画面）に着地し、Todayではない。ゲストにはまだ「今日」がない。所有トレーナーは現在の動作を維持（最後に閲覧したタブに戻る）。
- **表記：** どこにも「サインイン」なし。獲得動詞は**請求**（`READER_COPY.claimLine`正典：*君はこのチャンピオンになったのではない、請求したのだ*）。トレーナーコード（`components/trainer-code.tsx`）は「進捗を別デバイスに持ち込む」物語のまま。「トレーナー・シギル」としてフレームし、アカウントとはしない。

### 3.5 扉のフラグと計測

- `STORAGE.mSplash`（sessionStorage）。本セッションでスプラッシュを表示した。
- 新規クライアントイベント（機構は§5参照）：`m_splash`、`m_fly`（ゲストFlyタップ）、`m_guest_run`（初回ゲスト走行開始）、`m_claim_from_climb`（登りフックから養子縁組到達）。扉の成功指標は**ゲスト走行→請求変換**で、`/stats`で可視化。

### 3.6 モバイルの明示的非目標

- アプリストアビルド不要、別モバイルセーブ不要、アカウント不要（すべて`mobile.md` §4–5に従う。変更なし）。
- Watch／Today／Rankの剥離不要：シェルは全体を維持。ロビーの深み計画は維持し、§3の*デフォルト扉*のみ置き換える。

## 4. デスクトップ：スコープ変更なし、ただし一つの正直ルール追加

デスクトップ**は**製品であり、全体を維持：世界、Act 1、会場、リーグ、サガ。再設計は本決定に含まれない。二つのコミットメント：

1. **「どこでも出荷可能なオンラインゲーム」規律。** ゲームを普通のウェブゲームとして遊べ、完全で読みやすい状態に保つ（すでにそうである。Launch v0.1の六つのゲートがまさにこの基準）。将来のラッパー内でのみ意味を持つものは待機（オーバーレイSDK、プラットフォーム実績）。
2. **コアループの疑問は議論ではなく計測。** 「人は理解できるか？楽しいか？報酬を感じるか？」。§5がファネルを配線し、これらがダッシュボード数値になる。設計は数値が存在*した後*に反応する。

**インセンティブについて（「プレイヤーは何を得るか？」への正直な答え）：** 同一性（記録としての体）、地位（順位／順位表／戦争）、物語（サガ、ライバル）、純粋なスキルレーン一つ（登り／サーキット。トレーナーが演技する唯一の場所）。意図的に**収益約束はない**（§2.3）。プレイテストで報酬ループが薄いと判明した場合、レバーは*観戦*をより劇的にすること（討論行、ハイライト、審判）。外発的報酬の追加ではない。

## 5. 計測：ゲート1–2を仮定から数値へ

本ドキュメント全体で最もレバレッジの高い作業。現在ファネルは粗い（`session → claim → train → fight → return`；アナリティクスはまだ`bout`と言う可能性）。初回旅程のステップと初回進化までの時間は不可視。

### 5.1 新規イベント（集計カウンター。同一プライバシー姿勢、ユーザー別追跡なし）

`lib/server/track.ts`の`Z_EVENTS`を拡張：

```
fj_cinematic   // FirstRunシネマティック完了（スキップせず）
fj_pick        // 初回デュエルファネルでチャンピオン選択
fj_tune        // ドクトリン調整（初回旅程）
fj_duel        // 初回デュエル終了
fj_evolve      // 進化カード表示（報酬の瞬間）
fj_land        // コンコード着地到達
ttfe_u5 | ttfe_u8 | ttfe_over   // 初回進化までの時間バケット（5.3参照）
m_splash | m_fly | m_guest_run | m_claim_from_climb   // モバイル扉（§3.5）
```

すべて**クライアントイベント**（これらの瞬間を見るのはブラウザのみ）：`app/api/track/route.ts`の`CLIENT_EVENTS`に追加し、既存のfire-and-forgetヘルパー（`lib/track.ts`）で発火。アナリティクスは非致命的、レート制限、集計のみ。

### 5.2 発火ポイント（デスクトップ初回旅程）

| イベント | 発火場所 |
|---|---|
| `fj_cinematic` | `components/intro/first-run.tsx`。シネマティック完了 |
| `fj_pick` / `fj_tune` / `fj_duel` / `fj_evolve` | `components/intro/first-duel.tsx`。ファネルのステップ遷移（選択→調整→戦い→進化カード） |
| `fj_land` | コンコード着地ビート（`components/grounds/grounds-screen.tsx`、`guideWorld`ロジック周辺のガイド付きファネル／初回着地経路） |

各イベントは**ブラウザごとに一度**発火（`STORAGE`の既存初回フラグと並んでlocalStorageラッチ）。ファネルがリプレイではなくユニーク訪問者のステップとして読めるように。

### 5.3 ユーザー別追跡なしの初回進化までの時間（ゲート1）

トラッカーは集計のみのため、クライアント側でバケット化：初回セッション開始時に`performance`非依存の壁時計をスタンプ（localStorage、`lib/track.ts`の`new_user`ラッチと並んで）、`fj_evolve`発火時に`ttfe_u5` / `ttfe_u8` / `ttfe_over`（5分未満、5–8分、8分超）のいずれかを送信。サブ8分シェアが新規ユーザーの健全な過半数を占めるとき、ゲート1は緑。`/stats`で3本の棒グラフとして可視化。

### 5.4 ダッシュボード

`lib/server/track.ts`の`getAnalytics`（約83行目）のファネル配列を`fj_*`ステップで拡張し、`components/stats/stats-screen.tsx`でより深いファネル＋TTFEバケットを描画。「人はゲームを理解できるか？」を跳ねポイント付きのチャートに変換。

## 6. プラットフォーム（Steam、コンソール）：姿勢であり、プロジェクトではない

- **今：** 何もしない。ウェブファーストが戦略であり、妥協ではない。ゼロインストールがモバイル扉とシェアカードを成長として機能させる理由。
- **Launch v0.1の六つのゲートが緑になった後：** Steamリリースは*マーケティング施策*として実装（同じNext.jsビルドを包むラッパー（Electron／CEF級シェル））。注意すべき前提条件（ビルドではない）：オフライン耐性ブート画面、キーボード／ゲームパッドのみのメニュー通過経路、ナビゲーションのための可視ブラウザURLバー非依存。
- **コンソール：** 本物の移植＋認証＋おそらく本物のアカウントシステム。明示的にアカウント後（Phase 6）、現在のロードマップ上にはない。
- **それまでのルール：** ウェブ限定の*行き止まり*を追加しない（コアループ進行のために第二ブラウザタブや外部リンクを前提とする画面）。

## 7. 実施計画（順序付き；各スライスは単独で出荷）

> 工数規模：**quick**＝セッション内 · **session**＝集中セッション1回 · **deep**＝複数セッション。

### T0. 計測ファースト（デスクトップファネル＋TTFE）。*session*
§5の計装。可視製品変更なし。「理解できるか／楽しいか？」のすべての議論をデータでブロック解除。**モバイル扉に触れる前にこれを行う**ことで、扉の効果を初日から計測可能。
- ファイル：`lib/server/track.ts`、`app/api/track/route.ts`、`lib/track.ts`、`components/intro/first-run.tsx`、`components/intro/first-duel.tsx`、`components/grounds/grounds-screen.tsx`、`lib/stats-types.ts`、`components/stats/stats-screen.tsx`、`lib/brand.ts`（ラッチキー）。
- 受理：`/stats`に6ステップ初回旅程ファネル＋3 TTFEバケットを表示；イベントはブラウザごとに一度発火；`npm run build`＋lintクリーン。

### T1. ゲストフライト（アンロック）。*session/deep*
